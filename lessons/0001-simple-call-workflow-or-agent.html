Single call, workflow, or agent?

The first design decision in every LLM product, and the one interviewers ask about most.

Your mission
You are aiming at an applied LLM engineer role in 3–6 months. "How would you build X?" is the standard design question for that role. A strong answer starts by choosing how much autonomy the model gets, and says why.
Today's win
Given a product requirement, you can pick a rung (one call, one of five workflow patterns, or an agent) and defend the choice in two sentences.

Who decides the next step?

Anthropic groups every LLM-powered system that takes actions under one label, agentic systems, and then splits it in two.[1]

  • A workflow runs LLMs and tools along code paths you wrote in advance.
  • An agent lets the model decide its own process and which tools to use, and the model keeps that control as the task unfolds.

The whole distinction is one question: who chooses the next step, your code or the model? You will use that question constantly.

The ladder: climb only when you must

Anthropic's core advice is to find the simplest thing that works and add complexity only when it clearly improves results. Agentic systems usually buy better task performance by spending latency and money, so the trade has to be worth it.[1]

  1. 3. Agent most flexible, costliest, hardest to debug
    The model loops: choose a tool, observe the result, decide again.
  2. 2. Workflow predictable, tunable
    Several LLM calls wired together by your code. Five common patterns below.
  3. 1. One augmented call cheapest, start here
    A single model call, helped by retrieval, tools, and memory as needed.

Rung 1 is an augmented LLM: a model that can generate its own search queries, pick tools, and decide what to remember.[1] For many applications, a well-optimized single call with retrieval and good examples is enough, so you only leave it when you can show it falls short.

Rung 2: five workflow patterns

PatternWhat your code doesReach for it when
Prompt chaining Runs steps in order; each call consumes the previous output. Optional code checks ("gates") sit between steps. The task splits cleanly into fixed subtasks, and you will trade some speed for accuracy.
Routing Classifies the input, then sends it to a specialized prompt or tool. Distinct categories need different handling, and classification is reliable. Also used to send easy cases to cheaper models.
Parallelization Runs calls at the same time and merges results in code. Two flavors: sectioning (independent subtasks) and voting (same task repeated). You need speed, or several perspectives to raise confidence.
Orchestrator-workers One model decides the subtasks at runtime, delegates them to worker calls, and combines the results. You cannot predict the subtasks up front, such as a code change whose file list depends on the task.
Evaluator-optimizer One call generates; another critiques; loop until good enough. You have clear criteria and feedback measurably improves the output.

Parallelization and orchestrator-workers look alike. The difference: in parallelization you predefined the subtasks, and in orchestrator-workers the model works them out as it goes.[1]

Rung 3: the agent loop

Architecturally an agent is often simple: a model using tools in a loop, reading feedback from the environment each time. At every step it needs ground truth from the world, such as a tool result or the output of running code, to judge whether it is making progress. Stopping conditions, like a maximum number of iterations, keep it under control.[1]

Here is a sketch of that shape (my illustration, not code from the article):

messages = [user_task]
for step in range(MAX_STEPS):               # stopping condition
    reply = llm(messages, tools=TOOLS)      # model chooses: answer or tool call
    if reply.is_final:
        return reply.text
    result = run_tool(reply.tool_call)      # ground truth from the environment
    messages += [reply, result]             # feed it back; loop again

The price of this freedom is higher cost and the risk of errors compounding across steps, which is why Anthropic recommends testing agents extensively in sandboxes with guardrails.[1] Because the loop is so small, the quality of your tools largely decides how well it works, a theme we will return to.

A practical note on frameworks. The article suggests starting with direct LLM API calls, since many patterns take only a few lines. Frameworks can hide the prompts and responses underneath, which makes debugging harder.[1] The article also notes some of its tooling advice has aged since December 2024; the concepts above are the durable part.

Practice 1: recall it cold

Retrieval beats re-reading. Without scrolling up, write what you remember, then check yourself.

  1. Who chooses the next step: your code (workflow) or the model (agent).
  2. Prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer.
  3. Ground truth from the environment, such as tool results or code execution.

Anything missing? Those are the items to revisit, not the ones you got right.
